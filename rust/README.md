# ngx-waf-core

This crate contains the logic of the `ngx_waf` nginx module. The C layer only
registers the nginx module and directives, packs request data, drives the
asynchronous nginx operations and emits responses and variables.

ModSecurity is the only request-matching and blocking rule engine. IP, URL,
header, argument, body and other application rules are SecRules loaded through
`waf_modsecurity`. The Rust core retains four stateful flows around it:

* CC protection through `waf_cc_deny`;
* CAPTCHA through `waf_captcha` and `waf_action`;
* the Under Attack hold page through `waf_under_attack`;
* friendly crawler verification through `waf_verify_bot`.

There are no native black/white lists, rule files, regex-rule wrappers or their
inspection caches. `waf_rule_path`, `waf_mode` and `waf_cache` do not exist.

## Request pipeline

`waf_priority` accepts each of these inspections exactly once:

```text
VERIFY-BOT
CC
CAPTCHA
UNDER-ATTACK
MODSECURITY
```

The built-in order is the order above. A verified CAPTCHA session still runs
before the priority list. The retained inspections apply to every request
method; the CAPTCHA verification endpoint itself only accepts POST.

`waf_modsecurity on` requires at least one `file=` or a matching
`remote_key=`/`remote_url=` pair. A later `waf_modsecurity` in the same
context replaces the earlier instance. The loader runs while nginx reads the
configuration, so an unreadable or invalid rule file aborts startup.

## Layout

| file | contents |
| --- | --- |
| `src/abi.rs` | the `#[repr(C)]` vocabulary shared with the C glue |
| `src/ffi.rs` | the exported C entry points and panic guards |
| `src/config.rs` | directive parsing, validation, defaults and inheritance |
| `src/check.rs` | the request machine, priority chain and response resolution |
| `src/check/` | the per-inspection checks, shared cookie support and grouped tests |
| `src/modsecurity.rs` | libmodsecurity bindings and transaction lifetime |
| `src/cc.rs` | CC counters kept in a shared memory zone |
| `src/action.rs` | CAPTCHA challenge entries kept in shared memory |
| `src/shared_memory.rs` | the frozen zone layout, lock guard and tables |
| `src/http_response.rs` | incremental parsing of CAPTCHA provider answers |
| `src/data.rs` | embedded block, CAPTCHA and Under Attack pages |
| `src/util.rs` | time/size parsing, random strings and hashing helpers |

## C ABI

The interface is declared in `include/ngx_http_waf_ffi.h`, generated by
cbindgen from `src/abi.rs` and `src/ffi.rs`:

```sh
mise run header
```

CI regenerates the header and fails if the checked-in file changes. Only the
ABI vocabulary crosses the boundary. The C side owns configurations, request
views and inspection handles; Rust never retains a pointer whose owner does not
outlive the operation that uses it.

The request view contains only data still needed by the core: client address,
method, decoded URI, User-Agent, Cookie headers, body, transaction fields for
libmodsecurity and the shared memory zone handles. Arguments and Referer are
read by libmodsecurity through its own request view rather than duplicated in
the common request structure.

## Shared memory

CC counters and CAPTCHA action/failure entries live in nginx shared memory
zones. The layout is frozen and versioned because a reload reuses the same
segment.

All access goes through a lock guard. Every pointer is bounds-checked before it
is followed, table headers are validated before their slots are read, and a
remote client can write only an address, a count or flags. A corrupt zone is
rebuilt instead of being interpreted with an invalid layout.

`mise run test-rust`, AddressSanitizer, Miri, cargo-fuzz and the valgrind suite
cover this code. The sanitizers use a fake segment with redzones; valgrind
covers the module inside nginx.

## Building and testing

The supported entry points are mise tasks:

```sh
mise run build
mise run test-rust
mise run test-nginx
mise run test-e2e
mise run fmt-check
mise run clippy
```

The crate needs stable Rust and libmodsecurity 3. `LIB_MODSECURITY` can name a
non-system prefix. nginx must include SSL support because the CAPTCHA provider
client uses nginx TLS.

The integration suite fetches ModSecurity and CRS test repositories on first
use. The CAPTCHA templates also need network access.

## Known limits

ModSecurity runs request phases only: connection, URI, request headers and
request body. Response phases are intentionally out of scope, so response
inspection and CRS phases 3/4 do not run.

`waf_verify_bot` checks the host name returned by the asynchronous resolver.
It does not walk additional PTR aliases. In strict mode, a failed lookup is
treated as a fake crawler.

The module has no native global exemption for all five inspections.
`ctl:ruleEngine=Off` disables ModSecurity only; it does not bypass CC, CAPTCHA,
Under Attack or crawler verification.
